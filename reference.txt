# Blockchain CTF Skill Research Brief

## Document Status

This file is a cleaned research brief derived from earlier planning conversations. It is input for the execution agent, not runtime instructions for the final skill.

All challenge names, dates, repository paths, vulnerability summaries, and third-party project descriptions below are research candidates until checked against a primary source. An entry may be useful even when only a writeup is available, but it must not be promoted into the benchmark corpus as verified metadata without an immutable upstream revision and a reproducible setup.

Use this evidence order:

1. official challenge source, release, deployment scripts, and verifier;
2. protocol/framework specifications and implementation source;
3. organizer or author writeup;
4. independent writeup;
5. this brief.

Remove tracking parameters from retained links. Record the commit, tag, or release used for any benchmark.

## Project Goal

Build a Codex skill that helps an agent solve authorized blockchain CTF challenges from artifacts to a reproducible exploit. It should specialize the agent beyond a generic smart-contract audit by enforcing this loop:

```text
acquire challenge artifacts
  -> identify platform, language, versions, and harness
  -> read setup and verifier
  -> express the observable win condition
  -> model actors, authority, assets, state, and trust boundaries
  -> load the relevant platform semantics
  -> rank falsifiable exploit hypotheses
  -> implement a native PoC
  -> compile and execute
  -> inspect errors, traces, events, and state deltas
  -> revise until the verifier passes or a precise blocker is proven
  -> report exploit, command, runtime evidence, root cause, and assumptions
```

The defining property is execution-backed verification. Static analysis, fuzzing, symbolic execution, writeups, and other agents may propose hypotheses. The challenge verifier or an equivalent native state transition decides whether the exploit works.

## Design Conclusions

### Verifier-first analysis

The solver should read deployment, setup, wrapper service, and success checks before searching for vulnerability patterns. The win condition must be represented as a concrete predicate over state, balance, ownership, object/account data, events, return values, or service output.

### State and asset modeling

The solver should build a compact model of actors, capabilities, trust boundaries, assets, and transitions. Modern challenges often depend on interactions between correct-looking components rather than one obviously vulnerable function.

### Platform-specific routing

A single Solidity checklist is insufficient. The final skill needs conditional playbooks for:

| Route | Semantics that materially change the solve |
|---|---|
| EVM/Solidity/Vyper | delegatecall and storage layout, callbacks, transient storage, CREATE2, assembly/bytecode, signatures, DeFi math, transaction ordering |
| Move/Sui | resources and abilities, object ownership, capabilities, shared objects, PTB composition, object identity/version, clocks, epochs, randomness |
| Solana | account owner/signer/writable checks, PDA derivation, CPI privilege propagation, account aliasing, serialization, native Rust/C memory behavior |
| Cross-chain | source event/state, observer/relayer, message format, attestation, replay state, destination execution, finality, decimal/accounting conversion |
| TON | asynchronous messages, bounce behavior, message modes/value/fees, account state and initialization, cell serialization, cross-instance state/economy |
| Stellar/Soroban | transaction source/signers/sequence/operations, assets/trustlines, Soroban authorization trees, storage TTL, host serialization |
| WASM runtimes | host ABI, serialization, submessage/reply and rollback boundaries, storage namespaces, migration/admin paths |
| Custom VM | state journaling and rollback, nested calls, exceptions, gas/refunds, opcode/host divergence, differential execution |
| Chain forensics | source/bytecode provenance, proxy resolution, traces, events, storage/account data, transaction ordering, reproducible fund flow |
| ZK integration | intended statement versus constraints, witness generation, public-input binding, field/range assumptions, proof encoding, verifier integration |

### Native exploit feedback loop

The solver should preserve the challenge's toolchain and iterate from real failures:

```text
generate the smallest compatible exploit
  -> build
  -> fix compiler/type/interface errors
  -> run against the original setup
  -> capture the first informative failure
  -> inspect trace/revert/state delta
  -> change one exploit assumption
  -> rerun
```

A process exit code or an LLM judgment is insufficient evidence. The solver must observe the challenge predicate or an equivalent state transition.

### Tool roles

Tools are optional and should be selected by the question they answer:

| Role | Candidate tools | Output status |
|---|---|---|
| EVM build and execution | Foundry, Anvil, cast, Hardhat | Runtime evidence |
| Static EVM analysis | compiler output, Slither | Hypothesis |
| Sequence/invariant exploration | Echidna, Medusa, native fuzzers | Counterexample to reproduce |
| Bytecode path exploration | disassembler, symbolic execution, Manticore-like tools | Candidate path to execute concretely |
| Move execution | chain-specific Move CLI and test runner | Transaction/object/resource effects |
| Solana execution | cargo, program-test, solana-test-validator, Anchor | Instruction/account/token effects |
| Chain investigation | RPC, trace APIs, explorers or blockchain-data connectors | Reproducible state/transaction evidence |
| Source acquisition | GitHub connector, gh, git | Pinned challenge artifacts |

Do not require a particular plugin, scanner, multi-agent framework, or paid service. The baseline must work as one agent using repository tools and native runtimes. Independent agents may explore separate hypotheses or run blinded evaluations when available and authorized.

## Technique Coverage and Priority

The historical sample suggests the following coverage priorities. These are design priorities, not claims about current CTF popularity.

| Technique family | Skill treatment |
|---|---|
| private storage, pre-0.8 overflow, basic reentrancy | Retain for introductory cases; do not center advanced evaluation on them |
| access control, signatures, nonce/replay, permit | Core EVM authentication path |
| DEX/accounting/rounding/partial fills | Core, with units and explicit formulas |
| proxies/delegatecall/storage collision | Core medium-to-hard EVM path |
| transient storage and new EIPs | Advanced EVM composition path |
| same-transaction composition and transaction ordering | Core across EVM and Move-style transaction models |
| Move object/capability/shared-state semantics | First-class non-EVM path |
| Solana accounts/CPI plus native memory hazards | First-class blockchain-plus-pwn path |
| relayer/attestation/cross-chain accounting | First-class multi-component path |
| TON/Stellar/WASM semantics | Platform-discovery and native-semantics path |
| custom VM rollback/opcode/host divergence | Expert implementation path |
| chain forensics | Source-free evidence path |
| ZK constraints and verifier integration | Advanced crypto/protocol path |

## Benchmark Tiers

### Deterministic synthetic suite

Create small redistributable fixtures for CI. Each fixture must expose a real setup and verifier, define forbidden shortcuts, and execute in its native toolchain. Include positive cases for each platform route and a negative case that penalizes fabricated vulnerabilities or success output.

### Priority public evaluation

Start with these nine high-information candidates after verification:

1. PP Farming 2: proxy and storage reasoning;
2. Outer Stellar: cross-chain relayer and attestation;
3. Lootboxes: Move/PTB composition;
4. Staking: resource aggregation and time invariant;
5. Transient Heist Revenge: transient storage, CREATE2, and callbacks;
6. CODEGATE DEX: multi-chain accounting;
7. Solalloc: Solana plus native memory corruption;
8. Teragas: VM rollback divergence;
9. Zoo: EVM assembly and memory/control flow.

### Coverage evaluation

After metadata verification, use the full catalog to measure breadth and difficulty progression. Do not vendor full repositories by default. Pin revisions and fetch into isolated workspaces. Keep solutions and scoring oracles outside the solver-visible artifacts.

## Instructions for the Execution Agent

1. Treat this document as a research backlog and design rationale, not final skill text.
2. Verify candidate links and claims against primary sources before copying them into references or benchmark metadata.
3. Record immutable revisions, licenses, setup commands, tool versions, and verifier locations for promoted benchmarks.
4. Do not expose solution/writeup material to the solving agent during blinded evaluation.
5. Convert repeated, validated reasoning failures into concise skill instructions; do not encode one challenge's solution as a universal rule.
6. Keep `SKILL.md` focused on routing and the core solve loop. Put platform details in references loaded only when relevant.
7. Use native execution evidence to decide whether instructions improve solving performance.
8. Update or remove entries that cannot be reproduced. Do not preserve claims merely because they appeared in the original conversation.
